# Разметка, оценка и агентный подбор

[← Обзор проекта](../README.md)

## Подготовка пакета

В UI запустите сбор с URL, целью и бюджетом пар. Команда `just dataset` выполняет анализ, сбор, индексацию и подготовку заданий:

```bash
just dataset https://doc.rust-lang.org/std/ \
  --goal "Собрать документацию Rust для поиска по API" \
  --run-dir runs/rust-eval --max-pairs 100
```

Для уже готового корпуса не нужно повторять обход:

```bash
just benchmark prepare \
  --corpus runs/from-plan/corpus.jsonl --index runs/from-plan/index \
  --goal "Проверить поиск по документации Rust" \
  --max-pairs 100 --output-dir runs/from-plan/annotation
```

Генератор выбирает документы, составляет запросы с помощью LLM и подбирает кандидатов поиском с разными весами BM25. `--max-pairs` — лимит пар запрос–документ, не страниц; фактический размер может быть меньше. Для разбиения нужны хотя бы два разных запроса. Каталог результата должен быть новым. `dataset` добавляет `annotation/` и `dataset-result.json` к артефактам сборки.

## Человеческая разметка и приём

В Gather можно разметить пары оценками 0–3, использовать горячие клавиши, экспортировать CSV и принять пакет. Черновик сохраняется в `ui-labels.json`; после приёма редактирование блокируется. Пакеты с тестовой разметкой ассистента помечаются отдельно.

| Оценка | Смысл |
| --- | --- |
| 0 | Документ не помогает ответить на запрос |
| 1 | Связан с темой, но почти не содержит нужной информации |
| 2 | Содержит существенную часть ответа |
| 3 | Напрямую и достаточно полно удовлетворяет запрос |

В CLI разметчику передают `annotation.csv`. Заполните `relevance` и верните все строки в UTF-8; можно менять оценки и порядок строк, но не состав пар или исходные поля. `source.json` хранит исходное задание для сверки и не передаётся разметчику.

```bash
just benchmark accept \
  --package-dir runs/from-plan/annotation \
  --annotations runs/from-plan/annotation/annotation.csv
```

Приём не вызывает LLM. Внутри `annotation/benchmark/` появляются `dev.csv`, `test.csv`, `dev.json`, `test.json` и `split.json`. JSON-части содержат `queries` и `qrels`; `split.json` хранит состав частей и метаданные, включая ссылки на корпус и индекс. Все пары запроса остаются в одной части, по умолчанию test получает 30% запросов с округлением вверх, при этом в dev остаётся хотя бы один запрос. Долю можно менять через `--test-fraction`; сохранённое разбиение не перезаписывается.

## Сравнение конфигураций

На странице «Оценка» выберите принятый пакет, добавьте именованные эксперименты и задайте `top_k`. Gather использует только запросы `dev`, но ищет по всему корпусу. Выдача показывает оценку или отметку «не размечен». Отчёты с настройками, метриками и выдачами сохраняются в истории.

В CLI набор передаётся явно; пример конфигураций — в [`examples/retrieval-experiments.json`](../examples/retrieval-experiments.json):

```bash
just benchmark evaluate \
  --dataset runs/from-plan/annotation/benchmark/dev.json \
  --index runs/from-plan/index --dense-build runs/dense-01 \
  --experiments examples/retrieval-experiments.json \
  --output runs/from-plan/evaluation.json --top-k 10
```

Оба индекса строятся из одного корпуса; Dense должен быть [заранее загружен в Qdrant](retrieval.md#dense). Для сравнения только BM25 `--dense-build` не нужен. Существующий отчёт не перезаписывается. Оценка не требует LLM.

- Метрики: nDCG@k, Precision@k, Recall@k и Judged@k; для Precision/Recall порог релевантности — 2. Recall при неполной разметке относится только к известным релевантным документам, а Judged показывает покрытие выдачи оценками.
- Настройки подбирают на `dev`; `test` оставляют для проверки выбранной конфигурации. Локальная smoke-разметка ассистента проверяет пайплайн, но не доказывает улучшение выдачи. Готового репрезентативного набора с человеческими оценками в репозитории нет.
- Общий исполнитель переиспользует выдачи каналов внутри запуска при совпадении запроса и глубины (для BM25 также весов полей). Время включает эффект кэша и не является замером холодной задержки. Метрики учитывают итоговую позицию, даже если scores равны; исходные scores сохраняются в отчёте.

В Python используйте `RetrievalExperiment` и `evaluate_retrieval_experiments` из [`mas_crawler.benchmark.retrieval_experiments`](../src/mas_crawler/benchmark/retrieval_experiments.py); прежний BM25 API (`ExperimentSpec`, `evaluate_experiments`) сохранён. `queries` сопоставляет ID запросов с уникальными текстами, `qrels` — ID и URL с оценками 0–3.

## Агент оптимизации BM25

В Gather на странице «Оценка» выберите источник с готовым индексом и принятый пакет, затем задайте бюджеты в блоке «Оптимизация BM25». CLI-вариант сохраняет отчёт без применения победителя:

```bash
just benchmark optimize \
  --package-dir runs/from-plan/annotation \
  --output-dir runs/from-plan/optimization-01 \
  --top-k 5 --max-experiments 12 --max-model-calls 8
```

1. Сначала оцениваются три пары весов (заголовок, текст): `(1, 1)`, `(3, 1)`, `(1, 3)`. Бюджет экспериментов включает эти варианты; значение `3` не вызывает LLM.
2. Модель может предложить пакет новых весов, разобрать выдачу отдельного dev-запроса или остановиться. Пропорциональные веса не запускаются повторно; при выполнении пара нормализуется по максимальному весу. Лимит вызовов модели не является денежным лимитом; провайдеру могут передаваться фрагменты документов.
3. Победителя по nDCG@k выбирает код среди конфигураций с достаточным `Judged@k` (`--min-judged`, по умолчанию `0.8`). При равенстве побеждает более ранний вариант. Если ни один стартовый вариант не покрыт разметкой достаточно, причина остановки — `insufficient_judgments`.
4. `--patience` (по умолчанию 3) ограничивает последовательные пакеты без улучшения больше `--min-improvement` (по умолчанию `0.001`). Порог влияет на остановку, но не отбрасывает лучшую измеренную конфигурацию.

Агент читает `dev.json` и метаданные разбиения, не читает `test.json` и не меняет разметку. Корпус, `dev` и метаданные проверяются на изменение во время запуска. Пакет не содержит копий корпуса и индекса: их соответствие исходной разметке нужно сохранить.

`report.json` атомарно обновляется по ходу работы и сохраняет выдачи, метрики, решения, бюджеты, причину остановки и сравнение с лучшим стартовым вариантом. При ошибке провайдера уже измеренные результаты остаются в отчёте. Фоновый запуск в Gather можно открыть из истории после перезагрузки страницы.

В UI настройка «Автоматически применять победителя» включена по умолчанию. После успешного запуска допустимый победитель становится серверной конфигурацией BM25 для источника и переживает перезапуск API. Ошибка или недостаток разметки не заменяют активную конфигурацию; изменение корпуса делает её неактивной. В «Поиске» можно временно переопределить её кнопкой «Изменить для запроса».

Ограничения: подбор только BM25, без автоматической оценки на `test`, возобновления прерванного запуска и прямого экспорта победителя из отчёта.

```bash
uv run --locked --no-sync pytest tests/test_experiment_agent.py tests/test_web_optimization.py
```

Python-тесты используют временный Tantivy-индекс и контролируемые ответы модели. Браузерные проверки запускаются [общей командой](operation.md#диагностика-и-проверки) и подменяют ответы API. Эти проверки подтверждают работу цикла, а не качество выбора живой модели.
